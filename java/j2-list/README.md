# J2. Синхронизированный доступ к списку

Программа добавляет введённые строки в начало списка, а несколько потоков сортируют его пузырьком. Строки длиннее 80 символов разбиваются на части. Пустая строка выводит список, Ctrl+D завершает программу.

## Запуск

Нужна Java 21. Команды выполняются из `java/j2-list`.

```bash
./gradlew installDist

# Свой связный список с блокировками отдельных узлов
build/install/j2-list/bin/j2-list -t 4 -d 1000

# Collections.synchronizedList(new ArrayList<>())
build/install/j2-list/bin/j2-list -t 4 -d 1000 --impl array
```

`-t` задаёт число сортирующих потоков, `-d` — задержку в миллисекундах внутри шага и между шагами.

Тесты:

```bash
./gradlew test
```

Бенчмарк:

```bash
./gradlew benchmark --args="-t 1,2,4,8,16 --seconds 10 -d 100 --size 100"
```

Каждая реализация измеряется отдельно. `--seconds` — длительность одного замера, `--size` — число строк в списке. Результат — общее число выполненных шагов всех потоков, а не число обменов или полных проходов.

## Расчёт числа шагов

Пусть T — число потоков, d — задержка, τ — время замера. Время и задержка берутся в одинаковых единицах.

На каждом шаге сравниваются два соседних элемента. Поток ждёт d под блокировкой и ещё d после её освобождения. Без ожидания чужих блокировок за время τ один поток выполнит примерно τ / (2d) шагов.

В своём списке на время шага блокируются три соседних узла: предыдущий и два сравниваемых. Если потоки не мешают друг другу, получаем:

$$S_{linked} \approx \frac{T \cdot \tau}{2d}$$

Это оценка без учёта конкуренции за узлы. Реальное число шагов будет меньше из-за ожидания блокировок и накладных расходов.

У `synchronizedList` весь шаг выполняется под общей блокировкой. За время τ через неё может пройти примерно τ / d шагов. При этом сохраняется ограничение на скорость каждого потока:

$$S_{array} \approx \min\left(\frac{T \cdot \tau}{2d},\ \frac{\tau}{d}\right)$$

По этой оценке одного потока недостаточно, чтобы постоянно занимать общую блокировку. При двух потоках достигается предел τ / d, и дальнейшее увеличение их числа уже не даёт ускорения.

## Результаты замеров

Задержка — 100 мс, длительность — 10 с на каждую реализацию, список из 100 случайных строк. MacBook Air, 8 ядер, Java 21.

| Потоков | Свой список, оценка | Свой список, замер | `synchronizedList`, оценка | `synchronizedList`, замер |
|---:|---:|---:|---:|---:|
| 1 | 50 | 49 | 50 | 49 |
| 2 | 100 | 96 | 100 | 96 |
| 4 | 200 | 161 | 100 | 97 |
| 8 | 400 | 310 | 100 | 97 |
| 16 | 800 | 463 | 100 | 96 |

У `synchronizedList` результат с двух потоков остаётся около 100 шагов: ограничением становится общая блокировка. Отклонение от оценки связано с накладными расходами и тем, что `sleep` не гарантирует пробуждение ровно через заданное время.

Свой список при увеличении числа потоков выполняет больше шагов, но отстаёт от оценки: потоки ждут друг друга на соседних узлах, особенно в начале прохода. При 16 потоках получилось 463 шага против 96 у `synchronizedList`, то есть примерно в 4,8 раза больше.

Дополнительные замеры своего списка при той же задержке и длительности:

| Строк | 4 потока | 16 потоков |
|---:|---:|---:|
| 10 | 178 | 193 |
| 100 | 161 | 463 |
| 1000 | 156 | 459 |

На коротком списке увеличение числа потоков с 4 до 16 почти не помогает: слишком много шагов требуют одних и тех же узлов. Для 100 и 1000 строк результаты близки — в этих замерах увеличение длины списка заметного выигрыша не дало.
